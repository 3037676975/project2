About Project

项目介绍

Project2 不是为了展示一个复杂业务，而是专门验证“AI 写代码 → GitHub 保存 → Webhook 触发 → 宝塔拉取 → 服务器更新”这条链路能不能稳定复用。

为什么做这个项目？

过去每次修改网站，都需要复制代码、进入服务器、上传文件、覆盖目录。Project2 把这些重复动作拆开：代码只在 GitHub 里修改，服务器只负责自动同步，最终形成一套更接近真实开发团队的版本管理和部署方式。

核心原则：GitHub 是源代码唯一真相来源，服务器不手动改源码。

这套工作流解决什么？

  • 减少手动上传文件和覆盖错误。
  • 每次修改都有 Git Commit，可以回溯历史。
  • ChatGPT 可以直接围绕仓库持续迭代。
  • 同样的模式可以复制到 PHP、Node、Python、Docker 项目。
  • 部署失败时可以从 Webhook 日志和 Git 日志定位问题。

Deployment Guide

部署指南

下面记录的就是 Project2 实际使用的部署顺序。以后换服务器或新建项目，可以照着重新搭一遍。

GitHub 创建仓库

仓库名 project2，确保先有一次 Commit，让 main 分支真正存在。

宝塔使用 Git 创建站点

仓库填写 HTTPS 地址，分支选择 main，网站目录设置为 /www/wwwroot/project2。

处理 safe.directory

如果出现 dubious ownership，先把项目目录加入 Git 信任列表。

配置 GitHub Webhook

在项目 Settings → Webhooks 中粘贴宝塔生成的 Webhook URL，事件选择 Push。

Push 触发部署

ChatGPT 或其他开发工具提交到 main 后，GitHub 自动通知宝塔拉取。

检查部署日志与访问

宝塔 Git 管理中确认部署成功，再检查 Nginx、宝塔防火墙和云服务器安全组。

Frequently Asked Questions

常见问题

这里保留这次搭建过程中最容易再次遇到的问题，方便以后直接查。

为什么宝塔获取不到 main 分支？
如果 GitHub 仓库还是空仓库，main 只是默认分支名称，还没有真正产生 Git ref。先创建 README.md 或 index.html 并完成第一次 Commit，然后回宝塔刷新分支。
为什么 Webhook 明明触发了，但服务器没有更新？
先看宝塔 Git 管理 → 部署记录。如果日志出现 fatal: detected dubious ownership，执行 git config --system --add safe.directory /www/wwwroot/project2，然后再次 Push。
出现 dubious ownership 是什么意思？
这是 Git 的安全机制：执行 Git 的用户和仓库目录所有者不一致时，Git 会拒绝操作。只把你明确信任的项目目录加入 safe.directory，不建议全局通配所有目录。
为什么 GitHub 已更新，但 43.172.76.33:28438 打不开？
Git 拉取成功和公网访问是两件事。检查网站是否运行、Nginx 是否监听 28438、宝塔安全端口是否放行、云服务器安全组是否允许 TCP 28438。
以后还能直接在宝塔文件管理里改代码吗？
技术上可以，但不建议。服务器本地修改可能在下一次 Git Pull 时被覆盖或造成冲突。正确方式是修改 GitHub，再由 Webhook 自动同步。
这套方案只能部署 HTML 吗？
不是。静态 HTML 最简单；PHP 通常 Git Pull 即可；Node / Next.js 需要安装依赖、构建和重启 PM2；Python 需要安装依赖并重启服务；Docker 可以在拉取后执行 docker compose up -d --build。
API Key、数据库密码应该放哪里？
不要放进公开 GitHub。真实秘钥放在服务器环境变量或 .env 文件，并加入 .gitignore。Webhook Token、SSH 私钥、数据库密码同样不要写进公开仓库。

从“手动上传”升级到“自动部署”

Project2 的价值不是这个页面本身，而是验证了一套以后可以重复使用的开发基础设施。新项目只需要复制同样的 GitHub + Webhook + 宝塔流程即可。
